## Ranked findings and opportunities

### CXS-01 — P1 / measured bottleneck: legacy GIF Save/drag still performs whole-clip synchronous conversion and compression

**Locations:** `src/App.svelte:645` (whole-clip `frames.map(mask)`), `src/App.svelte:659` (hover export), `src/App.svelte:364` (busy wrapper), `src/lib/save.js:186` (fileBytes), `src/lib/gif.js:67` (legacy encodeGif), `src/lib/gif.js:73` (whole-clip output allocation), `src/lib/gif.js:78` (synchronous frame encoding loop).

**Ownership/trigger:** A 1-bit Save or prepared desktop drag owns full-resolution masks for every source frame. `converted` constructs all masks synchronously; the encoder allocates its entire worst-case output buffer and compresses every frame in one loop. Source pixels remain published/immutable; masks and compression buffer are export-owned. Full-palette streaming export has a different, cooperative/acknowledged path.

**Evidence:** Dungeon cutout masks took 244 ms first call and 428–509 ms warm in run 1; run 2 took 774 ms first / 486–1274 ms warm. GIF encoding took 527 ms first / 477–612 ms warm in run 1, and 1484 ms first / 580–1550 ms warm in run 2. Warm medians are 444/613 ms for masks and 529/1151 ms for encoding. Preserve the variance; do not advertise a single best result. Full masks alone are 13,131,776 bytes. The encoder's explicit buffer formula reserves 26,321,920 bytes for this source before omggif bookkeeping and final Blob/file storage.

**Call-graph check:** `during` posts **once before** a large job so the spinner can paint. It does not yield inside `frames.map(mask)` or `encodeGif`. `fileBytes` being async and awaiting a dynamic import does not split the synchronous loop that follows; a warm import's promise continuation is not an input/rendering task boundary. `saveAll` processes items sequentially but does not split a single GIF's loop. This supports a main-thread blocking risk when those same synchronous kernels run in the browser; it does not supply a newly measured browser duration.

**Expected/observed:** Import workers improve import responsiveness, but a real user's later legacy export still reaches these uninterrupted kernels. Expected goal is input opportunities during large exports with unchanged output. Observed source + Node evidence show the remaining path, not corrupted exports. Confidence high in synchronous ownership/cost, medium in its current device impact until UI profiling.

**Smallest proposal/tradeoff:** First add posted-task-separated **per-frame legacy mask and GIF compression** work with the same encoder/algorithm and captured settings. This is smaller than a new general export worker and preserves bytes/pixels; it may slightly lower throughput. One huge frame's mask/LZW remains a residual stall. Avoid an eager RGBA bake. If that residual is significant on actual fixtures, separately agree a narrowly scoped worker or cooperative kernel.

**Acceptance:** Built desktop and phone Save/drag of this GIF, all relevant 1-bit styles including None, ZIP containing several GIFs, settings changes during preparation and failures with no partial download. Compare every actual output frame against the old baseline independently, including dimensions, alpha, delays/loop/disposal. Measure task/input gaps and end-to-end throughput over repeated cold/warm runs. Unit/core output parity plus a witness that input runs between frames is needed. Already run: baseline suite/build, core profile. Remaining: all those UI/native/export before-after checks; no implementation is approved yet.

### CXS-02 — P1 / measured bottleneck: live-wall 1-bit reanalysis remains synchronous despite import workers

**Locations:** `src/App.svelte:511` (toItem), `src/App.svelte:520` (reread), `src/App.svelte:527` (pre-effect), `src/lib/recolor.js:123` (analyze), `src/lib/recolor.js:166` (unify), `src/lib/recolor.js:96` (whole-source seam scan). Export callers also reread before their busy wrapper at `src/App.svelte:699` and `src/App.svelte:730`.

**Ownership/trigger:** Changing a legacy Brightness source or applicable Opacity cut replaces source analysis for live items; original RGBA is reused. That pre-effect maps the whole wall, and `toItem` maps all animation frames then unifies them in one synchronous call. Published originals must not be transferred to the unpublished-import worker route.

**Evidence:** Reanalyzing/unifying the dungeon takes 261/265 ms first luma calls, 242–316 ms warm, with per-process warm medians 245/243 ms. Green calls take 289/293 ms first, 278–293 ms warm, medians 281/284 ms. This is one uninterrupted core call; no async loop surrounds it in the App pre-effect. The drag guard skips work above one million pixels while dragging, but performs it on settling/release; it moves the stall rather than making the final work cooperative. A change to a style whose stored brightness source differs can trigger the same upgrade.

**Root cause/confidence:** Workers cover initial unpublished imports/reprepare, not published wall analysis. High confidence; this is already acknowledged as an open target in the brief. No new normal-path stale publication was demonstrated.

**Smallest proposal/tradeoff:** If actual UI measurement warrants implementation, use cooperative frame-separated reanalysis with immutable request settings and atomic final publication. Keep existing completed previews while pending. Cancellation/item removal/family switch must prevent obsolete analysis publication. This bounds multi-frame batches but not a huge analyze or shared seam scan. Do not reuse `reanalyzeImported` on published sources; do not transfer live RGBA. Avoid promising zero stalls without a separately measured inner-loop change.

**Acceptance:** Repeated dungeon + many-large-still legacy source/cut/family transitions on desktop and phone; rapid superseding edits, clear/reimport and export during pending analysis. Compare every legacy auto threshold, seam/histogram and full/sample mask against the exact old path. Confirm no extra source copies or detached live buffers, and explicit request publication identity. Report responsiveness versus total preparation latency. Already run: profile/source trace, normal/GC tests/build. Remaining: actual browser/phone reproduction and agreed async-lifetime tests.

### CXS-03 — P2 / reproduced lifetime issue in controlled harness: obsolete hover preparation stays subscribed and delays newer jobs

**Locations:** `src/lib/export-drag.js:40`, `src/lib/export-drag.js:48`, `src/lib/export-drag.js:70`, `src/lib/export-drag.js:71`, `src/lib/export-drag.js:126`; `src/App.svelte:659`; `src/lib/palette-state.js:37`, `src/lib/palette-state.js:49`, `src/lib/palette-state.js:53`, `src/lib/palette-state.js:57`, `src/lib/palette-state.js:61`.

**Ownership/trigger:** After hover's 180 ms delay, the drag controller retains its captured request as `running`. Leaving/Cancel hover/refresh/destroy cannot cancel `prepare`; `fullPaletteImage` acquires generated/subset/cleanup work without a signal and converts full source. This subscriber therefore outlives the abandoned hover. Explicit Save subscribers intentionally have different lifetime needs.

**Witness:** With the actual baseline drag helper and generated client, begin hover preparation, cancel hover, and request generation for a new source. Thirty ms later the canceled hover's controlled worker is un-terminated; the new request remains pending and total start messages remain one. Completing the old generated result permits the second start. This establishes lifetime and queue ordering independently of performance timing; the controlled worker's deliberate pause is not ordinary app throughput. The same limitation was documented previously in palette implementation research.

**Expected/observed:** No new work should be owned solely by a hover that the user abandoned. Observed work continues and retains source snapshots until completion. No obsolete rendered/drag-file publication occurs: the helper checks current request and revokes/discards a stale completed record. Confidence high in wasted/retained work, unmeasured in native UI impact.

**Smallest proposal/tradeoff:** Give **only the preparatory hover job** an AbortController; thread it through `prepare`, `fullPaletteImage`, generated/subset/cleanup subscriptions and quantization. Cancel on leaving, supersession and destruction. Keep independent Save/viewer/preview subscribers alive. Preserve active native drag records and their grace-period URLs; a preparatory cancel must never revoke a native consumer's current file. Allow for warm-hover reuse so ordinary mouse jitter does not introduce avoidable duplicate exports.

**Acceptance:** Delayed dynamic import, queued/running/shared worker cases, abandoned hover, new hover/settings, removal/destroy, and canceled final quantization/encoding. Prove last hover cancellation terminates/removes only its request, while same-key Save/preview keeps it alive. Native Windows drag acceptance must preserve decoding/file identity and 60-second grace. Measure newer-preview latency and abandoned CPU on actual dungeon/large stills. Already run: deterministic lifetime witness and existing baseline suite. Remaining: signal-aware tests plus native desktop/device behavior after agreement.

### CXS-04 — P2 / missing terminal-event coverage, injected failure witness: four serial clients ignore messageerror

**Locations:** `src/lib/palette-generated-client.js:18`, `src/lib/palette-generated-client.js:22`; `src/lib/palette-limit-client.js:37`, `src/lib/palette-limit-client.js:45`; `src/lib/palette-cleanup-client.js:37`, `src/lib/palette-cleanup-client.js:41`; `src/lib/image-import-client.js:29`, `src/lib/image-import-client.js:36`. Contrast `src/lib/gif.js:183`, whose export worker already handles `onmessageerror`.

**Ownership/evidence:** Each active serial client installs `onmessage`/`onerror` and an abort handler. The diagnostic injects only the supported unreadable-message event at the browser-facing Worker boundary, with another job queued. All four have an undefined messageerror handler; first and second promises remain pending and worker remains live. Last-subscriber abort cleans/terminates and rejects both. A no-signal export subscriber has no equivalent user-triggered release and can indefinitely hold its source/queue if this event occurs.

**Important limitation:** Production messages are plain objects/typed arrays/Blob data. I have not reproduced a normal supported-browser deserialization failure from those payloads, nor established its frequency. Message passing does not imply spontaneous frame corruption. This is a demonstrated **missing event/error contract under injected failure**, not an observed ordinary threading defect or evidence for request-ID rewrites.

**Smallest proposal/tradeoff:** Add onmessageerror to each existing terminal failure path and clear it with the other handlers. Preserve semantics: palette clients reject/release; import client re-decodes immutable File unless aborted; GIF export behavior remains unchanged. Guard settlement and worker identity while touching handlers. No timeout/polling or protocol rewrite is justified by this evidence. Tiny additional handler/test cost; fail-fast is appropriate if the runtime reports unreadable data.

**Acceptance:** Inject on startup, after first transfer/partial import result and before publication; verify terminate, handler/listener cleanup, queued next-request recovery and source collection. Verify one-of-many abort separately from last-subscriber abort, including an explicit unsignaled export that receives the failure. Import must recover from File with actual detached inputs and preserve abort precedence/no fallback after abort. Test no-Worker parity separately. Already run: injected four-client queue witness, existing actual structured-clone transfer/subscriber tests and explicit-GC cases. Remaining: the proposed handler regression tests and affected built-browser/phone smoke checks. Defer if reviewers judge the rare event outside scope; do not inflate it to P1 normal breakage.

### CXS-05 — P2 / measured opportunity: structural 1-bit first preparation escapes the tile's drag budget

**Locations:** `src/App.svelte:249` (Stencil automatic-cut summary); `src/Tile.svelte:208`, `src/Tile.svelte:209`, `src/Tile.svelte:210`; `src/lib/recolor.js:203`, `src/lib/recolor.js:251`; `src/lib/icon.js:40`, `src/lib/icon.js:44`, `src/lib/icon.js:246`.

**Ownership/trigger:** First Stencil or Icon for an analysis/outline walks the full source before sampled mask timing begins. App's Stencil automatic-cut summary also calls spritesOf across source analyses; controls can trigger preparation before the Tile call. `pace` and `shown` budget only the later sampled mask, intentionally excluding preparation. Cached structural arrays remain on that live analysis; Auto/Keep/Trim Icon variants cache separately.

**Evidence:** On deterministic transparent 1MP noise, fresh Stencil takes 91/62 ms first calls and 53–191 ms warm-fresh, warm medians 62/103 ms. Fresh Icon Auto takes 294/370 ms first and 166–522 ms warm-fresh, medians 233/511 ms. Deleting the diagnostic's cache between samples measures fresh preparation, not repeated Detail slider hits. Cached Detail sampling is a separate fast path. The timer in Tile cannot use these costs to downscale preparation because structure depends on full-source connectivity. Node variance is large and browser/device timing is not established.

**Memory/confidence:** Icon allocates 15 bytes per source pixel in the directly visible arrays (including 2 retained output bytes), plus component scratch; all three outline variants can retain 6 bytes/source pixel. Stencil retains 3 bytes/pixel and can allocate another 5/pixel traversal scratch for transparency. This is useful caching on live analyses, **not a demonstrated leak**. Confidence high in unbudgeted source-wide synchronous work, medium in current real-art UI impact.

**Smallest proposal/tradeoff:** First measure actual first style/outline changes on supplied large art and phone. If actionable, move/defer full-source preparation using existing results and cancellation, then publish only the current analysis/outline. A kernel rewrite or sampled structural computation would alter output and is not justified. Cooperative components/rows are plausible but substantial; defer until the profile distinguishes one huge component from many smaller ones. Do not automatically evict all outline variants; that trades memory for repeated CPU.

**Acceptance:** All 11 styles, all Icon outline choices, source/cut reanalysis, viewer/resize and cancellation; exact full/sample mask parity including small-sprite cavity fixtures. Track first/settled output and main-task gaps, retained/scratch memory and repeated outline toggling on desktop and phone. Already run: first-prep source profile, unit suite/build. Remaining: real-art/device impact and algorithm-equivalence checks if an implementation is agreed.

## Challenges, retractions and rejected optimizations

- **No normal stale-cache or source-detachment defect found:** identity-based caches depend on immutable app sources, and transferring fresh slices is correctly different from shared-memory mutation. Canceled jobs cannot publish through guarded preview/worker paths in inspected source/tests. Finite tests do not prove absence of bugs.
- **Retain completed pixels is intentional:** fullReady separately controls converted timers; same-item pending frames may display the previous completed image. Original timing reads its predicate before readiness. Do not report that continuity as stale completed publication.
- **Limiter malformed-result idea deferred:** its client does not fully validate index cardinality/duplicates/pass sequencing, unlike generated/cleanup validation. A malicious/injected own-worker result could exceed cap; no current own-worker production path producing it or stale cross-job contamination was demonstrated. The worker and client are shipped together, no external untrusted response channel exists, and message tasks preserve order. Do not justify a protocol-ID rewrite or broad defensive validator from that hypothesis. A minimal validation test may be considered if future worker changes need a contract.
- **No universal import-worker speedup:** prior phone tiny-batch controls remain slower than pre-worker (421→586ms) despite better GIF responsiveness. Those are historical observations, not newly repeated timings. New benchmarks preserve cold/first-call data and broad variance; no larger warm-only still cutoff is proposed.
- **Memory budget is not app budget:** existing docs already disclose this. The retained Off cleanup map and active native URL grace are intentional and not mislabeled leaks. WeakMap lifetime and35explicitGC checks are useful targeted evidence, not proof that native/GPU/process memory returns to baseline.
- **No speculative fitting/kernel rewrite, candidate Set optimization, full-RGBA animation bake, downscaled export, source-color merging, eager optional imports, worker pool or new dependency proposed.** Exact/full-source output and cancellation remain acceptance requirements.
- **No browser deserialization failure claimed:** CXS-04's injected event cannot establish its normal-app incidence. Its narrow fail handler is robustness, not repair of demonstrated spontaneous corruption.
