# PixelLab service and Smart colors handoff audit

Date: October 15, 2026. This is a **vendor evidence audit**, separate from neutral implementation research spikes. No Colorfetti production source changed. Installed extension inspection was read-only; this document records interface observations without copying extension code. Smart colors integration is research only and is **not authorized for implementation**.

## Current live service checks

The official [REST schema](https://api.pixellab.ai/v2/openapi.json), [REST index](https://api.pixellab.ai/v2/llms.txt), [MCP guide](https://api.pixellab.ai/mcp/docs) and authenticated MCP tools were fetched again. The current public reducer still exposes automatic fitting, an explicit 2–256 count or supplied palette image, shared equal-size frames, and none/2×2/4×4/8×8 dithering with strength 0–10. The current REST schema does **not** accept `target_palette` on `/reduce-colors`; an actual bounded request returned 422 `extra_forbidden` for that field. MCP `reduce_colors` and `create_image_pro` expose no Smart field. This is narrower than the installed extension's observed Smart reducer UI.

Four fresh REST reductions and one fresh MCP reduction completed. All inputs were retained owned fixtures. Credentials were read from `PIXELLAB_SECRET` and sent only to the official API authentication surface; no credentials, configuration values or signed links are retained. All five responses reported 0.1 subscription generations, **0.5 total**, confirmed by before/final balance difference. USD credits were unchanged. The MCP output was saved to the account gallery by the service, an expected documented side effect. No new Pro image generation was submitted.

Results are in [fresh comparison](../../bench/palette-handoff-service-review/comparison.json), [independent verification](../../bench/palette-handoff-service-review/verification.json), [MCP output check](../../bench/palette-handoff-service-review/mcp-result.json), and the [source/output gallery](../../bench/palette-handoff-service-review/comparison.html). Independent Sharp decoding checked actual returned PNGs and current production PNG exports, rather than screenshots or service count labels.

All four pairs retained dimensions, all source alpha bytes and strict fixed-target membership. The armor outputs differ at 48 visible pixels. The prior source-matched [armor strength sweep](../../bench/palette-paired-comparison/armor-strength-sweep-results.json) shows strength 20 retains the connected highlight and all four colors. Challenge default discoverability and low-strength usefulness with a broader art corpus before adding controls or changing algorithm/default strength. A single sprite does not justify a hard-coded guard. Off remains the default.

REST wall-clock latency here was 595–1,119 ms. The corresponding current production module runs were approximately 16–36 ms on desktop Node, including generation/subset where needed and PNG encoding. **These are different execution environments and workloads**, not a mobile performance comparison. Actual desktop/mobile responsiveness, memory and animation remain browser/device test responsibilities. No claim of universal speed or visual superiority follows.

## Smart colors (beta): exact question and current boundary

The installed Aseprite extension reports version **0.4.130** and its read-only inspected UI contract defines Smart colors in the ordinary Reduce colors workflow when selecting a palette or a palette from the current frame. The local copy may contain edits; its clean published-release provenance is not established. This was not an interactive extension test. Its interface specifies a single image/frame, no dithering and an additional 15–60 seconds. The observed request contract supplies source pixels, dimensions and explicit target RGB colors with `smart: true` to the extension's quantization service. This is **existing-art semantic recoloring**, the relevant potential integration question. It is a different surface from public REST `/reduce-colors`; public API/MCP contract parity must not be assumed. We did not reproduce its private transport or retain account-specific extension configuration.

The older retained [Smart generation result](../../bench/palette-service-research/api-smart-analysis.json) successfully used `/generate-image-v2` with supplied colors, cap and Smart. It generated **new artwork** and then mapped it. It verified target membership and a semantic-looking result, but did not return the unmapped source and therefore cannot establish improvement over our conversion of the same image. **Do not treat that result as testing the extension's Smart recoloring operation.** Do not pay for another new-image generation just to repeat that invalid comparison.

Root-agent Codex Browser inspection reached PixelLab sign-in; no new authenticated website output or Smart absence is claimed. Four retained website outputs remain verified for their prior exact settings. If the authenticated website later exposes Smart on an uploaded existing source, test it there against the exact same owned source and target. Otherwise **defer existing-source Smart evaluation to the human's Aseprite extension UI**. Current public REST/MCP evidence alone does not supply a supported integration path.

### Deferred human extension experiment

1. Open copies of the retained item-sheet and tiny armor fixtures, plus a human-authored character with skin, eyes, clothing, metal and wood. Keep the source unchanged and record its file hash/dimensions. Use the same explicit opaque palette on every comparison; retain exact swatches/order.
2. With one frame and dithering Off, save three outputs: current Colorfetti nearest Oklab, extension ordinary Reduce colors, and extension Smart colors. Record all settings, extension version, request completion time and reported charge. Run a second Smart request on one source only if cost and latency are acceptable; measure repeatability separately from quality.
3. Inspect at 1× and enlarged nearest-neighbor scale. Check face/wood/material roles, tiny eye/highlight retention, outlines, silhouettes and local clusters. Independently decode outputs and check dimensions, every alpha byte, target RGB membership, used-color counts and unchanged geometry. A prettier result that redraws the sprite is a different feature contract.
4. Include a two-color target and a broader chromatic target. Record failures, refusal and lost details, not only attractive examples. Smart is documented as single-frame; do not extrapolate animation stability or silently process a clip frame by frame.
5. Decide **research outcome only**: worthwhile semantic recoloring, no benefit, or inconclusive. Before any later integration proposal, require a supported public endpoint for existing pixels, privacy/upload consent design, authentication ownership, costs, cancellation/retry, error handling and mobile latency evidence. Browser-only local recoloring remains the current app contract. No integration code should be written in this review.

## Review scope and required challenge

Read the vendor evidence directory `docs/research/pixellab-review-2026-10-14/` and retained `bench/palette-service-research/`, `bench/palette-paired-comparison/` and `docs/research/2026-10-15-auto-refinement-service-comparison.md`. Historical proposals there are time-stamped; they must not be described as current missing features. Current dithering, alpha Keep, used-color feedback, curated additions and Lospec import are implemented. Direct Auto fitting was rejected after broader downstream regressions; reopening it needs a new concrete hypothesis and evidence, not another identical sweep.

Use at most two review/fix iterations. In the first, list reproducible correctness/performance issues and concrete minimal fixes, or explicitly state no issue. In the second, independently rerun the failed cases, relevant regressions and desktop/USB Android behavior and settle the decision. Disagreement must resolve with a measurement or explicit deferred boundary, not endless review. Retain adversarial negative findings. Exact target membership is a hard gate; aesthetic preference and an Oklab average are separate assessments.

Vendor-free implementation spikes must not gain extension paths, source lines/excerpts or vendor implementation details. Keep this vendor audit and the handoff's navigation separate from those neutral spike documents.

## Reproduction without accidental charges

`node bench/palette-handoff-service-review/verify.mjs` is offline and safe. It validates retained PNGs and builds the side-by-side gallery. `compare.mjs`, `probe.mjs` and `mcp.mjs` contact the official service: `compare.mjs` reuses retained standard reductions but still sends a Smart validation probe and balance read; `mcp.mjs` refuses to resubmit a retained completed result. Do not delete retained response/submission/result files just to rerun research. New calls need a bounded missing-test rationale. `probe.mjs` refreshes only free schemas, MCP listing and balance; avoid overwriting historical before-balance if repeating it.
