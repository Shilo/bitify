# MP4 support — deferred task

Date: October 11, 2026
Status: Deferred; feasibility tested, app support not implemented.

## Decision and constraints

MP4 import with animated GIF export is worth considering for short sprite clips.
Reuse browser video decoding and Colorfetti's existing animation/conversion/export
pipeline. Avoid adding a video codec dependency, backend, or broad video editor.
The user's priorities are a small app download and little additional complexity.

Defer MP4 export separately. Native recording is possible in some browsers, but
consistent frame timing, codec availability, recording lifecycle and transparency
handling need additional work. Do not bundle FFmpeg merely to guarantee MP4 output.
The user subsequently requested a one-off MP4-to-GIF conversion, then asked to
record these findings as a deferred task. Neither prototype nor that conversion
adds MP4 support to the app.

## Findings from the supplied file

The local fixture was `lyHqFsTwT22P3WK.mp4`, supplied from the user's Downloads folder.
It is not checked into the repository.

| Property | Observed value |
| --- | --- |
| File size | 14,581 bytes |
| Video codec | H.264 |
| Dimensions | 220 × 220 pixels |
| Duration | 4.7 seconds |
| Frame rate / count | 10 fps / 47 frames |
| Audio | No audio stream |

A desktop headless Edge prototype used a local Blob URL, an HTML video element,
and canvas readback. It sought to the midpoint of each known 100 ms frame interval,
then extracted all 47 frames at original dimensions. The extraction loop took
323.2 ms in a single run, including canvas readback and base64 serialization.
There were 45 distinct extracted pixel buffers; this is not evidence of dropped
frames, since consecutive source frames can look identical. The test did not
independently prove exact decoder frame selection against all original frames.

The resulting buffers passed through the existing `analyze`, `unify`, Cutout
`mask`, and `encodeGif` functions. A looping black-and-white GIF was 46,788 bytes.
This proves reuse of the conversion pipeline for this fixture, not a finished
import flow or general MP4 compatibility.

All source RGBA buffers together used 9,099,200 bytes (about 8.68 MiB), before
analysis arrays, masks, conversion caches, encoder buffers and browser decoder
memory. A small compressed video can therefore become a substantial in-memory
animation. Desktop results do not establish mobile performance or safe limits.

Edge also returned `true` for
`MediaRecorder.isTypeSupported('video/mp4;codecs=avc1.42E01E')`.
No MP4 was recorded, and support detection is not a guarantee that an export will
succeed or retain exact timing.

The separate original-appearance GIF requested by the user was converted using
the locally installed FFmpeg CLI with `palettegen` / `paletteuse`, without Colorfetti
styling. FFprobe confirmed 220 × 220, 47 frames and 4.7 seconds. That desktop tool
is not a dependency or proposed implementation for the browser app.

Prototype files were left in the ignored `.tmp/` directory:
`mp4-feasibility.mjs`, `mp4-feasibility.gif`, and `lyHqFsTwT22P3WK.gif`.
They are local scratch artifacts, not durable fixtures or required dependencies.

## Proposed implementation scope

- Accept local MP4 files through the artwork picker and file drop route. Palette
  import and remote video URL support are outside this initial scope.
- Decode locally with the browser's video element; use canvas only to acquire
  source pixels, as the still-image importer already does. Continue using the
  existing direct GIF encoder for converted output.
- Produce the existing `{ frames: [{ original, delay }], loop }` representation
  used by `App.svelte`, so tile playback, original comparison, 1-bit/full-palette
  conversion, GIF download, ZIP export and still PNG copy can be reused.
- Load the video importer on demand. No new runtime package is expected. A small
  JavaScript module is plausible, but added compressed bytes have not been measured.
- Treat the result as a silent looping animation. Explain that video audio is
  omitted; preserve original pixel dimensions for supported imports and exports.
- Show import progress, allow Remove all to cancel decoding, and release the Blob
  URL, video resource, canvas, listeners and timers on every exit path.
- Report unsupported codecs, unreadable files, timeouts and limit failures clearly;
  continue importing the rest of a batch.

MP4 is a container, not one codec. Browser decoding determines which files work;
the successful H.264 fixture does not imply every MP4 is supported.

## Open decisions before implementation

1. Choose explicit duration, dimension, frame-count and total decoded-pixel limits
   using mobile measurements. Reject oversized clips before retaining their full
   frame collection. Consider the cumulative memory of multiple imports as well.
2. Choose and document a sampling rate. The prototype knew the fixture's 10 fps
   rate from FFprobe; a browser video element does not directly provide arbitrary
   source frame rates or a complete timestamp table. A fixed sampling rate is the
   simplest option, but changes high/variable-frame-rate sources and must be disclosed.
   Handle the final partial interval and very short clips without changing duration
   or creating invalid GIF delays.
3. Validate seeking and decoded-frame readiness in Safari/iOS and Android. The
   prototype only exercised desktop Edge and did not test a mounted import UI.
4. Keep MP4 output out of the first implementation. Revisit only if conditional
   native recording offers enough value to justify its timing and lifecycle code.
   Define an opaque background for output because ordinary H.264 MP4 does not
   preserve Colorfetti's transparent pixels.

## Completion criteria for the deferred task

- The supplied clip imports as an animation, compares with its original and
  exports a valid GIF at 220 × 220 with the documented sampling/timing behavior.
- Both conversion families, ZIP downloads and first-frame clipboard copy work.
- Cancel, malformed/unsupported inputs, short clips, final partial frames and
  oversized/cumulative-memory cases are verified without retaining abandoned jobs.
- Desktop and mobile browser checks cover file picker/drop, progress and recovery;
  actual Safari/iOS and Android video decoding are validated before broad claims.
- Measure the production build's added raw and compressed bytes, lazy loading,
  import time and peak memory. Reassess scope if it becomes dependency-heavy.
- Update the behavior spec, Help, import notices, README and performance record
  together with the implementation. Until then, existing image/GIF behavior stays
  the source of truth.
