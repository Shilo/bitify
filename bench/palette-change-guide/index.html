What changed since f08d4d3?

Six new capabilities: full-palette dithering, output color counts, direct output-palette reuse, two curated presets, Lospec-link import, and optional opacity preservation. Additional fixes protect displayed colors, PNG import, copying and long captions.

See the number of colors actually used

Preview now offers Count output colors. The count comes from full-resolution conversion; for an animation it includes all frames. Empty pixels do not count. Before: no count control. After: eight colors counted.

Before, the existing import dialog started empty. Now “Use 8 output colors” opens an unsaved eight-color draft. Name and save it locally or download its HEX backup. Saving/editing/HEX backup already existed; direct reuse is new.

Fixes and safeguards

Palette swatches resist forced darkening

Controlled forced-dark browser experiment. Original and current palette values are identical; the fix changes how the UI paints the swatches, so browser darkening does not substitute their displayed colors. Test-only browser emulation is recorded in the fixes receipt.

Firefox: partly transparent PNGs keep their brightness

Historical matched real-app Firefox captures immediately before and after the decoder fix, not a new phone run or an f08 build. Firefox exposed premultiplied RGB values that were imported as ordinary RGB, darkening partly transparent pixels. Current code uses the established canvas fallback for those frames. Small low-alpha rounding remains.

Changes a screenshot cannot prove

  • PNG import accuracy: Chromium can copy proven native sRGB bytes without an unnecessary conversion, preserving faint RGB colors more accurately. Firefox’s unlabelled premultiplied frames take the fallback instead. Pixel/byte evidence is required; a screenshot is not proof of exactness.
  • Reliable Copy: a failed clipboard setup no longer leaves an unhandled background error while PNG preparation is still running. The Copy button’s appearance did not change. Clipboard transport may still round partly transparent colors; Save PNG remains the exact route.
  • Long captions: output counts remain visible in dense image walls. The baseline has no count feature, so its caption cannot reproduce the intermediate count-layout regression.
  • Safer transparent export: Keep uses RGBA PNG where needed. A GIF that would lose partial opacity is rejected, and a ZIP is downloaded only if the whole export succeeds.
  • Settings consistency: previews, count/reuse, save/copy and animation export capture the same settings. Canceled sliders and obsolete jobs cannot publish stale results.

Artist-controlled color protection · design only

Not implemented. These are the previous illustrative mockups, copied unchanged for review. They do not demonstrate a working recoloring feature.

Choose an original color and its exact replacement

Protect the small detail you care about explicitly, for example turning the original muted red into the chosen red. Merely reserving a target palette entry cannot promise a particular eye or tabard will use it.

Review protected mappings and color-limit conflicts

  • Auto: protection requires stable target choices. The concept uses a fixed palette; applying it to a changing Auto palette remains undecided.
  • Exact color or region: matching an original RGB affects every eligible pixel with that RGB, not just the eye the artist tapped. Near-identical colors are separate; region-based painting is not proposed.
  • Color budget: protected target colors must fit the selected maximum. The app must explain conflicts rather than silently exceed the limit or discard a protection.
  • Cut and hidden colors: whether a protection always reserves a slot, or becomes inactive when its source color is hidden by the cutoff, remains undecided.
  • Discoverability: touch users need an obvious way to choose a source color, inspect the affected pixels and undo. Mockup layout checks are not human usability evidence.

Research completed, not added to the app

Direct-to-count Auto fitting, opacity-weighted palette fitting and automatic accent protection were tested and rejected because some artwork became meaningfully worse. No new weighting, automatic protection, quick 2/4/8/16 button row, or Smart colors integration shipped. Existing Auto, Matching, Max colors and Cleanup were already present at the baseline.

PixelLab comparisons are evidence, not a promise either product always wins. Smart colors on existing artwork still needs a human Aseprite trial; no supported public recoloring route was established.
